# BACKEND_BUILD → BACKEND_VERIFY → FRONTEND_READY

实施方法遵循 [implement.md](implement.md)。本文件约束阶段目标与交接，不规定编码或测试步骤。

## 开工条件与范围

核对真实 baseline 与 backend 授权，执行 check --for-build。当前版必须是活动版本，来源精确基线已交付，草稿与批准快照一致。
读全部本期后端任务、完整领域规则、权威契约、数据/迁移、权限/隔离、错误、非功能指标和接口消费者需求。
前期原型是需求输入，不是此阶段需要实现的生产 UI。开发接口测试、请求样例、契约校验器和必要 fixture，不把浏览器前端写完才测试后端。
全部本期后端能力应在前端阶段开始前就可独立验证；无新增后端变化的版本仍核验旧后端适用性，建立验证型后端任务和本版交接。

## 自主实现

依据批准规范与实际代码，自主拆分任务、安排后端实现与验证，发现问题后自行修复。可采用测试先行或其他适合本项目的方法，不要求固定循环或逐项请示；本阶段不跨入正式前端。
按风险选择足以证明真实行为的验证方式，不以空测试或全替身证明数据库/外部集成通过。
任务保持基线及 phase=backend 关联；颗粒度和阶段内次序可随实施细化，后端验收不依赖尚未实现的前端。

## 后端验收目标

以批准的必需验收为准，自主选择检查方式与深度。以下帮助识别适用风险，不是所有项目统一执行的测试清单；不要增加与本期范围无关的流程。

真实业务与数据：所有承诺接口实现；校验、唯一性、事务、幂等、并发、分页/排序/过滤、软删除/归属等与规范一致。
权限与安全：鉴权方案、角色与资源级授权、租户隔离、错误边界、审计和敏感字段不靠隐藏前端控件保证。
契约：把实际实现/实际响应与批准 contract 对照；字段名/类型/可空/枚举/格式、状态码、错误结构、时间/货币/精度、事件或文件上传均按需求验证。
数据生命周期：干净安装、指定来源版本带数据升级、兼容窗口和失败恢复，适用时验证历史客户端；不把“能回滚代码”说成“数据库可无损回退”。
独立可运行：按 runbook 可启动后端、准备隔离测试数据、执行 health 与代表性成功/失败请求，不要求正式前端就绪。
前端就绪：逐项对照原型操作和接口清单，不能留下“未来前端阶段再补”的必需接口、字段、权限或错误语义。
每项必需后端 AC/gate 真正通过；使用质量门槛模板细化，脚本无法自动证明这些语义。

## 完整交接包

交接输入写在 `.project-flow/versions/<版本>/handoff-input/`，不修改冻结规范。见 assets/backend-handoff.template.md 与 backend-handoff.example.json。
运行说明需给出依赖版本/锁文件、真实代码路径与精确修订、安装/启动/迁移/种子数据命令、重置开发数据的作用范围及风险。
环境模板只有变量名与非秘密默认值；鉴权测试账号说明用创建方式/角色映射，不写生产凭据；新会话重新获取秘密。
逐接口清单关联 REQ/AC/前端操作、实现位置、请求/响应样例、错误、验证证据，覆盖所有批准能力。
说明 base URL 配置、API 前缀、CORS/本地代理、cookie/CSRF 或 token 生命周期、分页与重试、上传/下载/异步状态等适用细节。
可重复冒烟说明给出命令、预期输出、数据准备和权限上下文。已知限制要说明不阻塞哪些验收；阻塞前端必需能力的事项不能列成“无影响限制”。

后端报告和交接输入齐全且真实验收通过后，先按 stage-controls 询问接受交接进入 FRONTEND_READY 还是继续调整；用户确认后，工具 accept-backend 检查阶段、精确规范、backend 必需检查、任务、证据文件和受管源码指纹，复制实际交接文件、后端任务、报告、证据和批准 contracts 到：

```text
docs/releases/<版本>/implementation/backend/h001/
├── manifest.json
├── HANDOFF.md
├── handoff.json
├── backend-tasks.json
├── verification.json
├── attachments/
├── contracts/
└── evidence/
```

hNNN 是后端验收交接修订，独立于产品版本和文档 bNNN。其中包含源码指纹而非完整源码备份；运行仍需对应后端仓库/构建产物。
copy/哈希能检查记录一致性，不能证明测试真正执行或实现真的符合设计。

## 停在交接点

accept-backend 成功后进入 FRONTEND_READY，不自动开始前端。更新 handoff、tasks、session-notes，制作 checkpoint，给出可复制的新会话提示。
报告明确区分“后端已验收”与“系统已交付”。不要在这一阶段调用 deliver 或改 current_delivered。
默认在此询问开始前端、继续调整后端或换会话；只有真实指令已明确确认这个转换，或明确免除此范围的重复提问，才直接顺序处理。仍准确记录 frontend 授权并核对交接，笼统“完整实现”不代表跳过询问。

## 后端重新调整

实现偏离原规范：按原业务修复，不改文档替错误实现辩护。已交接的后端先 reopen-backend，旧 hNNN 保留，任务标记 needs_revalidation；重新验收产生新 hNNN。
产品/接口/数据语义改变：先 revise，影响分析和新基线批准；后端代码可复用，但旧交接不自动适用于新基线。
新增非阻塞内部日志等变化也会改变观察指纹，工具保守要求重验；Agent 可缩小受影响检查，但不能伪造新执行证据。

## 两个阶段收尾点

BACKEND_BUILD 已具备独立验收条件时，展示完成范围、已运行检查与仍待验收项，询问“进入 BACKEND_VERIFY，还是继续修改后端实现？”不能把后续验收说成已通过。
BACKEND_VERIFY 真实通过后，展示报告、交接资料和限制，询问“接受本次后端验收，归档交接并进入 FRONTEND_READY，还是继续调整后端？”未回答前不调用 accept-backend。内部编码、排错和测试方法仍自主决定。
