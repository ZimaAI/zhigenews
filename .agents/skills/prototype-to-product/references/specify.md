# SPECIFY / READY：完整规范与前后端边界

从已经讨论和原型验证的结论整理规范，不重新发明产品，不重问已确定的选择。
每版本同时有完整需求/设计/契约与本期变化说明；实施计划只列本期增量。
需求、UX、领域、架构、验收、实施、差异、兼容迁移、交付计划可按项目规模合并，但必须有明确映射与可读内容。

## 冻结前补全

用户/角色/范围/不做事项明确；核心及失败流程、授权与数据归属、业务状态和不可变量明确。
数据拆分领域、交换、页面与持久化；contracts/ 是权威交换边界及必要引用/样例的完整集合，不把生成 DTO 作为主源。
后端职责、前端职责和公开接口分清；后端能独立验收，不要求正式前端先实现。所有原型操作都有对应接口或明确前端本地行为。
后端与前端实施计划、验收门槛、接口交接要求在基线中已定义；后端完成后才能进入正式前端。
适用兼容窗口、历史数据迁移、回退/前滚限制、旧客户端、升级矩阵已确定；无影响项目注明依据。

execution-plan.json 的 mode=backend-first；source_roots 指定后端、前端及各自必要共享配置的完整观察范围。
默认 pause_after_backend=true；false 只表达顺序连续工作的偏好，不免除阶段末尾询问、任何验收或阶段授权；免重复询问需用户明确说出具体阶段范围。
所有有效 AC 与 gate 明确 phase=backend/frontend/integration；每阶段至少有必需检查。长期稳定 ID 不重复编号。
模板只提供候选，不整套照抄为每项目的强制门槛。冻结目标、验收结果与重要约束，具体实现/测试方法留给模型；用户或项目明确规定的方法除外。
将“完整系统才可验”的场景放 integration；不要把必须通过浏览器才能验证的测试错误地卡在独立后端阶段。

## 基线与授权

`seal` 保存实际 draft 内容到新的 bNNN，不创建批准或开工。
`approve --kind baseline` 记录用户对精确基线的批准，进入 READY。
`approve --kind backend --code-ref <实际后端起点>` 才进入 BACKEND_BUILD。
`approve --kind frontend` 只能在后端交接成功的 FRONTEND_READY 运行，并绑定实际 hNNN。
用户可一句话批准规范与后端；前端条件授权必须有清楚原话，工具本身不验证自然语言语义。

新会话可以从 SPECIFY 的未完成文档或 READY 接续；检查点只记录续接，不等于批准。
任何有影响的冻结规范调整：revise → 编辑草稿/原型/契约 → 新 bNNN → 重批准。旧规范、批准、后端 hNNN 与证据保持历史，不复用旧通过状态。
源码缺陷但规范没变，无需伪造新需求；已交接后端使用 reopen-backend 走重验流程。

## 完整性与工具限制

脚本检查文件映射、编号/引用、阶段归属、最低必需门槛和 hash，不理解业务完整性、质量阈值、接口语义或用户身份。
readiness_reviewed=true 只能由实际核查后填写，不是形式开关；占位内容和模板示例不能直接冻结为已完成规范。
阶段结束更新 tasks/decisions/handoff 并 checkpoint；文档冻结不必结束会话，也不要求另开会话。

## 用户如何让 SPECIFY 进入 READY

完整使用示例见 [使用手册](../USAGE.zh-CN.md)，规则见 [阶段控制](stage-controls.md)。
候选尚不存在或资料不全：继续整理，真实核查后 seal，展示实际 VERSION/bNNN、关键范围、剩余问题与文档入口；保持 SPECIFY 等待批准。
候选已展示且未变化：用户批准该具体基线后，check 核对草稿、快照及阻塞，再 approve --kind baseline。成功才写 READY 并保存检查点。
“生成文档”“继续整理”“准备进入 READY”本身不授权新生成而尚未展示的规范。明确批准已经展示且唯一可识别的候选可以用自然语言，不强迫用户背工具命令。
用户在批准消息中同时提出语义修改时，先修改、生成新候选再请确认；不能先批准旧版后把变更偷偷塞进去。
用户要求停在 READY 时不得执行 backend 授权；状态显示 READY 仅表示规范获批，不表示后端开工或任何测试通过。

## 主动邀请用户决定

候选准备好后，不只留下“等待批准”或“下一句可发”。按 [阶段控制](stage-controls.md) 登记确认点，展示该候选，直接询问“批准此基线进入 READY，还是继续修改规范？”发问后保持 SPECIFY 并保存检查点。
选择修改就按冻结规则调整并展示新候选；选择推进先 answer-review，再 approve baseline。READY 中没有新任务可做时，询问开始后端还是继续审阅/调整，不擅自开始代码实现。
