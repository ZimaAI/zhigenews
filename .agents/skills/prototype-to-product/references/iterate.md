# DISCOVER / SCOPE / ITERATE：围绕真实变化讨论

## 首版与后续版本的差异

首版查目标用户、核心角色、第一条操作链与最小数据关系。足够展示第一版时就提出开始原型或继续调整范围的选择，不必先问完整个项目。
后续版本先读来源快照、本期诉求、受影响代码和测试；在保留旧行为的前提下讨论变化，不重做已确定的部分。
默认每轮提出 1–3 个独立关键选择，给推荐、代价与可逆默认值。事实由 Agent 查证，不让用户帮你翻代码。
仅有文档、没有实际源码时明确“当前可规划，后续在已有系统上实施需源码”；不把重新实现当作无声默认。

## 本期范围记录

将反馈分类为 added、modified、unchanged、deprecated、removed，并记录旧行为、新行为、影响的角色/页面/接口/数据/回归用例。
非本期诉求放到独立待办或后续版本，不混入当前基线。已有缺陷只有被纳入本版范围或属于必需回归阻塞时才处理。
用户原型反馈与原规则冲突时呈现冲突和影响；确定后记录被替代的决定，保留来源。

## 原型约定

默认位置 `docs/releases/<version>/draft/prototype/`，不进入生产构建。必要时沿用现有原型环境，但冻结前将必要源码和固定样例整理入规范树。
原型可启动、可点击、可重置，固定样例与可控时钟，不依赖真实生产数据。
请求经 adapter 集中处理，组件不散落硬编码业务结果。mock 明确标注，不代表真实鉴权、并发或性能已经正确。
继承的页面保留布局与行为，只有受影响页面才重新设计；仅在方向不明确时给关键页面少量不同方案。
纯后端补丁无新增页面可说明不适用，复用原有基准；涉及可见行为时不能仅交一段文字代替可运行原型。

## 四类数据

领域模型定义对象、关系、状态、不变量和归属；交换契约定义请求/响应/事件与错误；页面模型定义表单、分页、筛选与派生状态；持久化模型定义数据库约束、索引、事务与迁移。
四者关联但不强求同一个结构。跨 Java/Python/TypeScript 的交换格式使用语言中立规范，HTTP 默认选适用工具链支持的 OpenAPI 版本。
每个产品版本有自己的 contracts 主源；实现类型与 mock 从它生成或校验，不修改其他版本的旧契约。
新增字段同时考虑旧数据默认值、旧客户端、回填、空值语义以及是否真的是向后兼容；不由“只加字段”自动推断兼容。

## 一轮迭代闭环

1. 转换反馈为可验证行为变化，指向稳定的 REQ/AC/CHG ID。
2. 对照父版及当前已确认规则，分析冲突、保留范围与跨版本影响。
3. 联动修改交互、领域、权威契约、样例与数据映射。
4. 更新当前版完整规范草稿中的受影响部分，并维护本期差异；不重写无影响内容。
5. 验证原型启动、契约/样例、必要类型和核心流程；能使用浏览器就实际操作并记录观察。
6. 保存决定与下一步，递增原型 revision；展示变化及仍待用户选择的点。

不是要求严格先编辑哪一个文件；但回合结束前必须消除互相矛盾。无需在探索阶段生成完整生产测试套件。

## 交互状态与安全语义

按业务演示正常、空、加载、校验失败、服务失败、无权限、重复提交和成功反馈。
过期、撤销、额度、并发冲突、部分成功、超时等按相关性补充，不机械增设无意义状态。
每个本期可操作按钮都有真实的原型状态变化；范围外动作明确标识，不假装成功。
前端隐藏不是授权机制；服务端权限、租户隔离和数据归属须落入规范。

## 原型满意后的动作

当你判断本期原型和数据已具备定稿条件时，展示原型、数据变化和验证结果，主动询问“进入 SPECIFY 整理规范，还是继续修改原型和数据？”保存确认点，用户选择后才推进。用户认可局部页面不自动冻结整个版本。
正式文档在定稿时集中整理，但每轮决定已记录，不能最后从模糊聊天总结里重新猜规则。
