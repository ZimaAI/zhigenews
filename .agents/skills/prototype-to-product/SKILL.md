# Prototype to Product · 跨会话、多版本、后端先行

用户决定产品行为、范围与授权；你负责查证事实、展示原型、维护文档和真实验证。
本 skill 不依赖一条永久对话。**会话是工作窗口，项目文件是持续状态；换会话不重置版本、阶段或决定。**
正式实现先后端、后前端；阶段内的方法、测试与验证策略由模型自主决定，见 [实施总则](references/implement.md)。不规定固定切片或 TDD；已批准的验收和授权边界仍有效。

## 每次进入：先恢复，不重新发明项目

1. 读 `AGENTS.md`、项目实际工作区和用户已给信息。保留未提交/未跟踪修改，不擅自切分支、提交、reset 或清理。
2. 读 [sessions.md](references/sessions.md)。查 `.project-flow/project.json` 和目标版 state；优先用户明确版本，其次注册表 active_version，不用目录排序猜“最新”。
3. 对当前格式工作区运行 `version_flow.py resume --root . --version <版本>`，读返回的文件和检查点笔记。它只读，不会恢复旧代码、清除阻塞或启动下一阶段。
4. 只处理 `schema_version=4`、执行状态/计划 `workflow_version=4`。其他格式停止并说明不支持，不转换、导入或覆盖已有资料。没有受管资料时才初始化。
5. 核对目标产品版本、来源基线、当前候选/活动基线、阶段、源码位置/指纹、有效授权、下一任务。只加载当前阶段需要的参考与规范章节。
6. 用一句话说明“版本 / 基线 / 阶段 / 本轮动作”。已确认事项不重复采访；记录缺失或事实矛盾时只处理具体缺口。

新建项目/下一版本读 [versioning.md](references/versioning.md)。历史查询只读，不必切换工作版本。
缺检查点不是重头开始的理由：核对 state、tasks、decisions、现有代码及证据，补写续接资料后继续已授权任务。

## 生命周期：每行都支持新会话继续和受控调整

用户操作与阶段转换见 [阶段控制](references/stage-controls.md)；可复制用法见 [使用手册](USAGE.zh-CN.md)。阶段是任务状态，不是需要用户手工修改的配置。

| 阶段 | 当前工作 | 进入时读取 | 退出条件 |
| --- | --- | --- | --- |
| DISCOVER | 首版目标、边界、第一条用户流程 | [iterate](references/iterate.md) | 足够生成可运行原型 |
| SCOPE | 后续版本差异、来源代码、兼容影响 | [versioning](references/versioning.md) | 本期变化和保留范围清楚 |
| ITERATE | 原型、领域、契约、样例和验收同步迭代 | [iterate](references/iterate.md) | 用户明确要求定稿 |
| SPECIFY | 整理完整规范、前后端分工、差异与迁移计划 | [specify](references/specify.md) | 批准具体候选基线 |
| READY | 文档已批准，等待后端实施授权 | [specify](references/specify.md) | 明确授权该基线的后端 |
| BACKEND_BUILD | 实现全部本期后端，不实现正式前端 | [backend](references/backend.md) | 后端任务与受影响检查完成 |
| BACKEND_VERIFY | 独立验收后端，制作可复用交接包 | [backend](references/backend.md) | 后端必需检查通过，交接完整 |
| FRONTEND_READY | 后端已验收，等待前端启动；默认会话交接点 | [frontend](references/frontend.md) | 核对交接、代码、环境并取得前端授权 |
| FRONTEND_BUILD | 按已批准原型对接真实后端 | [frontend](references/frontend.md) | 全部本期前端任务完成 |
| FRONTEND_VERIFY | 前端构建、交互、角色、真实接口验证 | [frontend](references/frontend.md) | 前端必需检查通过且有报告 |
| INTEGRATION_VERIFY | 完整系统、新旧功能、兼容迁移与工程质量 | [delivery](references/delivery.md) | 全部必需结果齐全，交付归档 |
| DELIVERED | 查询/交接已交付成果 | [versioning](references/versioning.md) | 后续修改另建产品版本 |
| BLOCKED | 保存阻塞与 resume_stage | [sessions](references/sessions.md) | 真正解决阻塞，返回原阶段 |

切换会话不需要先完成当前阶段。BACKEND_BUILD 做到一半、SPECIFY 文档未定稿、FRONTEND_VERIFY 测试未通过，都可以保存并续接。
后端验收后默认停在 FRONTEND_READY，交付后端摘要、交接包和续接提示，不提前写正式前端。
每条阶段箭头默认都先询问再推进。只有用户已明确确认当前展示的转换，或明确要求在具体阶段范围内连续推进且不再逐阶段询问时，才免重复提问；一般的“完整实现”不等于关闭阶段确认。仍核对新成果、准确授权和所有验收门槛。

## 阶段收尾：主动给选择，不替用户推进

遵循 [阶段控制](references/stage-controls.md)。阶段内部自主工作；接近阶段末尾时先核查目标、产物、真实证据与阻塞，不按轮数、文件数量或模型自信判断完成。
已具备下一阶段条件时，先保存成果，以 `review-stage` 记录当前版确认点，再展示摘要、产物入口、验证/限制和下一阶段的具体含义，**直接询问“进入下一阶段，还是继续修改当前阶段？”** 可同时说明允许暂停。
发问后保存检查点并结束本轮，保持当前 stage；不能先切阶段再补问，也不能一边等待一边执行下一阶段。
用户选推进：核对确认点未过期，以 `answer-review` 记录真实回答，再调用对应的批准、阶段、验收或归档命令；选择不代替验收，不自动扩大到后一阶段。
用户选修改：保留当前阶段并落实反馈；冻结规范/已验收后端分别按 revise/reopen-backend 受控回退，修改后重新评估再询问。用户选暂停：保留状态，不继续写代码或重复催问。
新会话先恢复 `pending_stage_review`。仍待回复就恢复同一选择点；已回复且内容未变就执行已确认动作，不让用户重复批准。过期确认先展示变化再重问。
只读查询不触发写入或强制提问；中途有任务就继续做，不每个文件、测试或修复都提阶段确认。DELIVERED 是终点，不虚构下一阶段；BLOCKED 是阻塞处理，不伪装成阶段完成。

## 不可省略的约束

### 先用原型决定产品

前期仍需可启动、可点击、可重置的前端原型，mock 明确标识；“后端先行”只约束正式实现，不禁止先做 UI 原型。
每轮检查：场景 → 交互状态 → 领域规则 → API/事件契约 → 样例 → 验收 → 旧功能与迁移。
区分领域、交换、页面和持久化模型。每版只有一个权威交换契约；生成 DTO、客户端和 mock 不能另成主源。
原型源码可丢弃，已批准行为与视觉基准不可擅改。正式前端不得用“后端没有这个字段”自行删掉批准功能。

### 多版本文档仍完整、可追溯

读 [documents.md](references/documents.md)。沿用产品版本、bNNN 基线、原型修订的区别。
每版保留完整目标规范 + 本期差异；历史基线保存正文与指纹，不覆盖旧版，不靠拼接所有历史补丁理解系统。
REQ/AC/ADR 使用稳定 ID，删除保留 removed/retired 与理由。继承规范不继承任务完成、用户授权、后端交接或通过状态。
主源是批准快照；全局 INDEX、RESUME、会话摘要、后端交接只是导航或实施证据，不另起“最新需求”主源。

### 三种授权不能混用

分别记录 `baseline`、`backend`、`frontend`，绑定精确产品版本/基线指纹；前端还绑定实际验收的后端 hNNN 及其指纹。
用户可在同条清楚指令中批准规范并授权后端。认可页面不自动扩张到下一端或下一版。没有明确待确认问题时，“继续”只延续当前阶段；刚展示唯一确认点且明确说明批准/开工含义时，可按上下文解析“进入下一阶段”，范围仅限该转换。
新会话沿用可核对且未失效的既有授权；只换会话不要求重复批准全部规范。当前用户的明确暂停/限制优先。
授权记录是本地断言，不是身份证明；缺失来源、范围含糊或互相冲突时，不从摘要伪造授权。
部署、付费操作、生产密钥与数据破坏不在默认实施授权内。

### 后端交接是前端的依赖门槛

后端必须有真实业务实现、独立测试与契约一致性证据，不是“路由和表生成完了”。
交接包含批准契约、逐接口实现清单、启动/迁移/种子数据说明、鉴权/跨域/错误语义、环境变量示例、可重复冒烟和已知限制。
用 `accept-backend` 归档后端报告、实际交接文件、契约和源码指纹；不需要正式前端存在即可验收后端。
新会话实现前端前必须 `check-backend`；只读已批准规范与交接不够，还要实际核对服务、地址、角色和鉴权。
默认前端阶段不改后端公共接口。发现后端不符合原规范，用 `reopen-backend` 修复并重新验收；若要改产品语义/契约，则 `revise` 产生新基线重新批准。
旧 hNNN 保留，新交接不会沿用旧前端验收和对旧交接的授权。纯前端修改不应使后端指纹变化；共同配置变化需评估并重验。

### 每轮结束都留下可继续的项目状态

读 [sessions.md](references/sessions.md)。更新本版 decisions、tasks、handoff 与下一动作，保存未决项、验证命令、真实结果、失败和证据路径。
在有意义的工作结束、阶段切换、用户要求换会话或上下文将中断时，运行 `checkpoint`。不要等到收到“结束会话”才第一次保存。
检查点 cNNNN 记录当时状态和受管文件/源码指纹，**不等于新基线，也不备份完整应用源码**。
读取过期检查点发现差异时先核对当前工作区，不能用旧摘要覆盖现有文件、重做已完成任务或把失败标成通过。
同一工作区默认顺序交接、单个写入者；此 skill 不保证多个会话/机器同时编辑的事务一致性。

## 本轮报告

给出版本/基线/阶段、本轮实际改变、验证结果、产物入口及未完成项。达到阶段收尾条件时必须实际发出一次“推进或修改”的问题，不只写“下一句可发”让用户猜；未达到条件时报告具体剩余工作，不暗示已经完成。问题语气中立，不预选推进，不催促用户接受。
换会话时附可复制的续接提示；后端完成明确写“后端已验收，前端待实现”，不称整个系统已交付。
没有真实运行的测试、浏览器、数据库升级或集成不能报通过；离开当前执行后不承诺继续工作。
