# 阶段控制：阶段内自主，阶段末尾由用户选择

## 默认协议

每个正式阶段收尾时，AI 主动询问：**进入下一阶段，还是继续修改当前阶段的内容？** 用户也可暂停或换会话。
“阶段内自主实现/测试”不等于“自主跨阶段”。例如测试可以穿插 BACKEND_BUILD，但将状态推进 BACKEND_VERIFY 前默认仍有收尾确认；不要为单个任务、文件或测试请求确认。
这是阶段选择，不是每次都重新申请相同权限。baseline/backend/frontend 三类授权及原有验收检查继续保留。

## 什么时候询问

先核查当前阶段目标、必需产物、已执行验证和阻塞。DISCOVER/SCOPE 达到足以做第一版原型即可，不要求提前穷尽未来实现问题。
ITERATE 要有可查看的原型和同步数据；SPECIFY 必须先整理、核查、seal 并展示精确候选。BUILD 只声明“实现已具备独立验收条件”，不能把尚未执行的验收说成通过。
VERIFY 只有必需检查实际通过、证据及交接材料齐全时才提出推进；存在失败/缺环境时继续修复，或询问具体阻塞的解决方式，不提供虚假的“已完成，是否进入下一阶段”。
已获授权的目标内仍有可自主完成的工作时继续做，不用“你要不要下一阶段”替代应做的工作。

## 保存、发问、等待、处理

1. 保存本阶段成果、任务和实际证据。用 `review-stage` 记录 from/to、版本/基线、摘要、产物文件、非阻塞限制和内容指纹；SPECIFY 的候选先 seal 后记录确认点。
2. 向用户展示简短的成果与证据摘要，说明下一阶段会做什么，发出一个“进入还是修改”的问题。记录检查点后结束本轮；保持原 stage，不先执行下一阶段。
3. 以用户实际回答调用 `answer-review`。这只记录选择，不自动批准或切阶段；之后才用转换表中的正式命令推进。必要条件不满足时，即使用户同意，也如实报告缺口。
4. 修改或暂停则不执行推进命令。修改后重新核查，重新展示确认点；无需重复问全部需求。

`pending_stage_review` 保存在本版本 state.json；阶段名称不变，不额外引入一个遮蔽真实阶段的 WAITING 状态。
状态有 awaiting_user、advance_confirmed、changes_requested、paused；成功执行正式转换才关闭确认点，并在 history 留存。
同内容、同问题的重复 `review-stage` 复用 qNNNN，不应在没有变化时不断催问或生成新确认号。有变化后旧确认失效；qNNNN 不是规范基线或产品版本。
先保存将展示的资料再登记；不要把会话导航当验收证据。报告、日志和交接附件须用 `--artifact` 纳入确认范围，工具不会自动判断证据的充分性。

## 统一问法

```text
当前：<产品版本> / <基线或未冻结> / <当前阶段>
已完成：<本阶段实际成果与入口>
验证与限制：<已执行结果；未执行和非阻塞限制如实写>
下一阶段：<阶段名>，将<实际动作及授权范围>。

你希望进入下一阶段，还是继续修改当前阶段的内容？也可以先停在这里。
```

不要暗示“进入”优于“修改”，不默认勾选，不以用户沉默、换会话或额度不足推断同意。

## 转换表：每一行默认先确认

| 当前 → 目标 | 收尾时的选择含义 | 用户确认后的正式命令 |
| --- | --- | --- |
| DISCOVER/SCOPE → ITERATE | 开始可运行原型，或继续调整目标/本期范围 | stage --to ITERATE |
| ITERATE → SPECIFY | 当前原型和数据可以定稿，或继续改原型 | stage --to SPECIFY |
| SPECIFY → READY | 批准已展示的精确候选，或继续改规范；不授权开发 | approve --kind baseline |
| READY → BACKEND_BUILD | 开始后端，或继续审阅/调整方案 | approve --kind backend |
| BACKEND_BUILD → BACKEND_VERIFY | 实现已可验收，进入独立后端验证，或继续改实现 | stage --to BACKEND_VERIFY |
| BACKEND_VERIFY → FRONTEND_READY | 接受验收结果并归档交接，或继续调整后端 | accept-backend |
| FRONTEND_READY → FRONTEND_BUILD | 对接具体 hNNN 开始前端，或先调整/换会话 | approve --kind frontend |
| FRONTEND_BUILD → FRONTEND_VERIFY | 开始前端验收，或继续改实现 | stage --to FRONTEND_VERIFY |
| FRONTEND_VERIFY → INTEGRATION_VERIFY | 进入完整系统验证，或继续调整前端 | stage --to INTEGRATION_VERIFY --report ... |
| INTEGRATION_VERIFY → DELIVERED | 接受验证结果并本地归档，或继续修改；不部署生产 | deliver |

在 READY/FRONTEND_READY 不需要重复制造产物：展示已有明确批准/交接后，直接问下一阶段开工还是调整/暂停即可。
纯后端补丁经用户明确认可可不新增原型，DISCOVER/SCOPE → SPECIFY 必须展示理由，不默认跳过原型讨论。
BLOCKED 不询问“验收完成是否进入下一阶段”：保留原阶段，核对阻塞解除后恢复已授权工作。修复失败和安全回退可在原授权内执行，不必为内部排错反复询问。
DELIVERED 不存在自动下一阶段，只报告归档；只有用户要求继续新版本时才创建。

## 解释回答和已有授权

“进入下一阶段”“批准该候选”在唯一、已展示、内容未变的确认点中表示对该转换的确认；SPECIFY 必须已说明候选引用与“批准文档、不启动实现”，开工点必须已说明对应实施范围。
孤立的“好”“继续”、局部页面认可或全新会话没有恢复上下文的短回答不扩大授权；不明确时只澄清这一项。不要要求用户背命令或重复一长串编号。
“先改 X”“可以，但先改 X 再进入”优先解释为修改，不先批准旧产物。只调整文字表述是否属于规范修订，仍按冻结规则处理，不能静默改快照。
一次清楚指令可以批准已展示基线并授权后端，顺序记录即可，不再为这两个刚确认的转换重复询问。
用户若明确说“后端 BUILD 和 VERIFY 之间不再逐阶段询问，验收后停在 FRONTEND_READY”，记录原话与精确范围，仅对此免重复询问；一般的“完整实现”“自主测试”或 pause_after_backend=false 本身不关闭阶段收尾确认。
此类免重复提问不能预先批准未展示的新候选，不能忽略新阻塞、基线/源码/交接变化或当前暂停指令。恢复会话只延续可核对的有效选择，不新建授权。

## SPECIFY → READY 示例

```text
当前：v1.0.0 / b001 / SPECIFY
完整规范已整理并核查；候选入口为 docs/releases/v1.0.0/baselines/b001/snapshot/。
<这里列实际完成项、核查结果和仍适用的限制，不复制示例当作事实。>

是否批准 v1.0.0/b001 并进入 READY，还是继续修改这份规范？
进入 READY 只确认文档，不会启动后端或前端实现。
```

无候选先整理和 seal，不用“准备进入 READY”冒充批准未知文档。候选已存在且未变，不为批准重复 seal。
用户选修改时留在 SPECIFY；存在被冻结内容就 revise → 修改 → 新候选 → 重新询问。用户批准后才 approve baseline。
用户要求“批准并开后端”时可以合并处理；只批准文档时进入 READY 后再问是否开始后端或继续调整，不自动开工。

## 恢复和调整

先 resume；若 pending 仍待答且内容未变，恢复同一问题，不重新生成产物或切阶段。用户明确要求查看进度时只报告待确认，不强迫选择或写入文件。
已有 advance_confirmed 且指纹仍一致，继续正式转换，不因换会话重复批准。新产物/代码/任务/证据变化先展示差异，旧确认不能用于新内容。
用户选修改后保持当前阶段；涉及冻结规范需 revise，涉及已验收后端需 reopen-backend，并解释回退原因。已交付版本修改另建产品版本。
具体字段和参数见 [工具手册](tooling.md)。脚本只能阻止**已登记确认点**被绕过；没有登记的问题、模型是否真的询问、回答是否真实和语义是否准确，仍由 Agent 根据对话负责，工具不是权限沙箱。
