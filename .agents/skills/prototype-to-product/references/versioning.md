# 产品版本、文档修订与迭代链路

## 四种身份与三个指针

| 标识 | 例子 | 含义 |
| --- | --- | --- |
| skill 包版本 | 4.1.0 | 可复用工作流本身的发布，不是业务系统版本 |
| 产品版本 | v1.1.0 | 本次系统交付的范围，交付后不可重开 |
| 基线修订 | v1.1.0/b002 | 此产品版本的一次完整、不可覆写的规范快照 |
| 原型修订 | r8 | 未冻结探索期间的轻量回合编号 |

`active_version` 是当前会话/工作区在处理哪版；`current_delivered` 是用户指定的当前交付文档入口；目标版 state.active_baseline 是正式实施绑定的规范。它们不得互相代替。
实际线上跑什么由环境部署记录回答，不从上述字段推导。本工具不探测或更改线上版本。
版本标签建议用 v主.次.补丁，项目自行定义升级策略；工具不按标签大小自动选最新、判兼容或降级。

## 下一版本的最小闭环

1. 读取来源交付、来源基线、目标代码现状。来源必须具体到 `VERSION/bNNN` 和哈希。
2. 用户没有指定来源、但已经有明确的 current_delivered 时，展示以该版本为基础的建议；已有明确选择不再追问。
3. `new --from` 复制完整规范到目标 draft，记录来源；不复制用户批准、执行任务或验收通过状态。
4. 对本期反馈做新增/修改/保留/废弃/移除分类，记录“不改哪些已有行为”。
5. 先核对受影响模块和现有测试，演示变更流程；保持未变模块，不再次从头生成整个应用。
6. 完整规范与本期差异一致后冻结、批准、授权、实现、回归、归档。
7. 需要作为主要文档入口时，再以明确指令更新 current_delivered；不要把归档和生产部署混在一起。

`new` 会复制上个快照的语义单元、契约、固定样例、原型源码与 ADR；重置 scope 的版本、来源、差异摘要和 readiness_reviewed。
共享的文档标题不要硬写“这是永远最新的 v1”；版本身份统一从 scope.json 读取。继承后检查正文中的历史版本引用，按语义修正，不能无脑全局替换。

## 同版修订还是下一个产品版本

未交付、用户仍在完善同一轮范围：保留同一产品版本，`revise` 后创建 b002、b003。
已经交付的版本：哪怕是补丁或文档纠错，也新建产品版本。不要重写旧快照来让历史看起来一直正确。
纯排版/链接纠错需要新候选基线才能改变正在构建的规范指纹。重新批准时可以只展示准确的非语义差异，不重新采访产品。
执行进度、测试日志、任务状态不属于冻结规范，更新它们不需要改基线。

## 并存、热修复与前移

典型谱系：

```text
v1.0.0/b002（已交付）
  ├─ v1.1.0/b001（新功能研发）
  └─ v1.0.1/b001（修复旧线）
```

不能假定补丁自动进入新功能版。为修复建立稳定 CHG/BUG ID，分别记录各目标版本的适用性、合入状态、需求影响与回归证据。
若要把补丁合入尚未冻结的 v1.1.0，在完整草稿中合并，登记 `scope.incorporated_refs` 与变更记录。
若 v1.1.0 已冻结，则 revise、新基线并重新批准受影响范围；已交付则再开新的产品版本。
`incorporated_refs` 记录其他已交付谱系的精确基线引用，不取代主 parent；工具核对引用存在并已交付，但不证明代码真的合并了修复。
保持原 parent 并显式记录合入，比默默改掉 ancestry 更容易追溯。源码的三方合并及冲突解决由 Agent 结合代码完成，不由本脚本执行。

当当前主线为 v1.1.0 时，归档 v1.0.1 不自动倒退主线文档指针。`promote` 要求显式给出预期当前值，并检查来源/合入关系；跨谱系覆盖要有单独授权与理由。
这里的“文档指针回退”只改变导航，不回滚应用或数据库。

## 并行边界

允许任意多版本文档共存、查询和规划，默认一份工作区只构建一个活动版本。
切换目标前写好旧版本 handoff，记录其候选/活动基线、代码起点、未提交变动、工作树位置与当前任务。
`switch` 只改文档指针，不调用 Git，不移动生产代码，不保证 HEAD 正确。
需要同时实现两个版本时，先明确独立代码分支/工作树和各自状态的归属，避免两个 Agent 写同一份文件。不要把此本地单写注册表当作分布式调度器；需合并注册表时人工处理冲突并运行 doctor。

## 提前规划未交付版本

`--allow-unreleased` 仅在用户明确要求提前规划时使用，仍绑定来源的精确候选快照。
来源交付前工具拒绝下游构建；来源最后若以不同 bNNN 交付，不能偷偷继承新的内容或转移旧批准。
需要重新分析相对于新来源的差异，创建一个新的目标版本标签。默认脚本不提供破坏性的 rebase/重写谱系命令。
这是一项明确的工具边界，不把“能存很多版本”夸大为全自动分支合并。


## 会话与阶段交付

每个产品版本可在全部阶段跨会话接续；cNNNN 是会话检查点，不是产品版本。hNNN 是后端交接修订，不是规范 bNNN。
new 继承完整规范（包括 execution-plan），不继承检查点、hNNN、授权、验收或任务完成。
本期后端全部通过后再实现前端；无变化的组件只做适用性/回归验证，不为了阶段划分重写。
切换文档或新会话都不切换 Git，不自动改变远程部署。默认共享工作区顺序交接，不支持多个会话同时改同一版本状态。
