# 版本文档模板

这是语义清单，不是要求首轮就生成十份空文件。内容随讨论逐步形成；定稿前补齐并消除未决项。
小项目可以合并文档，scope.documents 映射每个语义单元到对应文件。版本身份统一写 scope，不每版批量改无关文档标题。
下列示例不代表用户已经批准任何具体产品。

## 00-index.md：版本阅读入口

版本与来源（引用 scope.json）；当前是否为草稿/候选；本版目标摘要；文档权威边界；阅读顺序；原型启动/重置方式；contracts 入口；实际代码起点；外部材料与固定版本；需要读的适用 ADR。
为新实现 Agent 说明：完整有效规范描述目标系统，06-implementation 描述相对来源代码的增量任务，07-changes 描述改变理由。

## 01-requirements.md：完整有效需求

目标用户、角色与任务；完整范围；明确不做；需求稳定编号和标题；场景、前置条件、成功/失败行为；不变量与权限语义；量化非功能条件；保留行为；废弃/移除的期限和替代能力。

| REQ ID | 本版状态 | 本期变化 | 有效行为 | AC ID | 不做/约束 |
| --- | --- | --- | --- | --- | --- |
| 按实际编号 | active/deprecated/removed | added/modified/unchanged/deprecated/removed | 明确的完整行为 | 实际链接 | 明确边界 |

不要把“保持和以前一样”作为唯一规范，完整目标行为应在本版可找到。

## 02-ux.md：交互与原型基准

路由/页面清单；角色与可见/可操作条件；主流程及分支；表单校验；加载/空/失败/无权限/成功状态；反馈与重置；适用的响应式和可访问要求；变化页面与未改基准；原型源码及样例；实际验证记录的引用。
无新增 UI 的补丁写明复用哪些旧基准及为何不新建原型，不把后端鉴权写成只隐藏按钮。

## 03-domain.md：完整领域模型

本版本词汇表；实体/值对象；关系与基数；标识与归属；状态机与允许/禁止转换；规则编号；不变量；时间/金额/空值；并发冲突；事务边界；删除/撤销/过期语义；新旧语义映射。

| 对象/字段 | 业务含义 | 类型与空值 | 约束 | 来源/状态变化 | 迁移影响 |
| --- | --- | --- | --- | --- | --- |

领域不是数据库表照抄，交换 DTO 与页面模型分别映射。

## 04-architecture.md：目标设计与本期影响

技术栈与明确版本依据；现有模块与变化模块；公开边界；主要数据流；认证/授权/隔离；持久化约束、索引、事务、锁/幂等；外部集成、失败/超时/重试；配置和秘密边界；观测、部署与运行；重要 ADR。
用最少足够的设计完成本期任务，不为每个小改动引入新的服务或框架。
接口详情引用本版 contracts，避免在多份文档手写重复模型。

## 05-acceptance.md：本版适用验收

每个 AC 包含：关联 REQ、适用性、新增/变更/旧功能回归/迁移类别、Given/When/Then、独立预期、运行环境、测试入口、必需性和合法的 N/A/豁免依据。
验收与实现分开：不要把被测算法复制一遍作为预期。此处记录定义，不填执行“已通过”。
有效旧 AC 继承定义，在本版重新取得证据。退休用例保留理由并新增必要的移除行为验证。

## 06-implementation.md：本期增量实施

代码起点/工作树位置；本期增量范围；前后端阶段边界与关键依赖；相关 REQ/AC/契约；可复用模块；暂不变更区域；重要升级约束与交付目标。
任务细化、阶段内顺序与具体实现/测试方法由模型在执行时自主决定，不预先冻结每步操作或命令，除非用户或项目已有明确要求。任务与执行记录放本版 tasks.json，不回写冻结文档。

## 07-changes.md：相对父基线的本期变更

目标版本；精确父基线/指纹；本期主题；明确保留的行为。

| CHG ID | 分类 | 旧行为 | 新行为 | 影响 REQ/AC/模块/契约 | 兼容性 | 用户决定引用 |
| --- | --- | --- | --- | --- | --- | --- |

补充不采纳方案与原因；受影响原型；数据映射；回归范围；跨分支需要前移/已合入修复；未解决问题。
每条变化必须落实到完整规范，不能只写在这张表。

## 08-compatibility-migration.md：兼容与升级

| 维度 | 原版本行为 | 目标行为 | 兼容/破坏/N/A及理由 | 迁移方式 | 对应验证 |
| --- | --- | --- | --- | --- | --- |
| API/事件 | | | | | |
| 数据库/历史数据 | | | | | |
| 客户端/集成方 | | | | | |
| 权限/租户归属 | | | | | |
| 配置/缓存/队列 | | | | | |

数据步骤：前置检查 → 备份/隔离演练 → 兼容结构 → 回填映射 → 校验 → 切换 → 清理（适用时）。
说明幂等、中断续跑、锁/性能、可支持旧版本窗口、过渡状态和验收条件。
区分代码回滚、数据恢复与前滚修复。不可逆处明确指出，不假设 downgrade 无损。

## 09-release-plan.md：验证、交付与操作边界

交付物与运行要求；适用安装/升级验收目标；必需 gate 及完成标准；规范符合性与工程质量要求；环境假设；代码/镜像标识；上线前提；功能开关与观察窗口；回滚触发条件；生产操作授权边界；文档指针是否更新。具体检查组合与审查方式由模型决定，实际命令记录在交付资料中。
正式交付的结果另放 delivery 归档；不为了补填日期而修改已冻结计划。

## ADR 模板

ID、标题、状态、适用版本/首次引入、背景与问题、候选方案、决定与理由、代价、影响的 REQ/CHG/模块、替代哪个决定、用户/技术证据引用。
旧决定被替代时在新版本中记录 supersedes；旧快照不回写状态。

## 决策/变更的最小记录

ID、时间/回合、用户原话或明确假设、旧规则、新规则、理由、影响面、决定状态、替代关系、需要迁移/回归/前移的版本。
高影响假设必须在基线前解决。聊天决定进入规范后以确切文档/规则引用追溯。

## handoff 模板

目标产品版本与阶段；精确来源、候选/活动基线；当前文档与代码指针；工作树状态；已经确认的决定引用；当前/已完成任务；实际命令与退出码；证据；阻塞；需要前移的修复；下一条可执行动作。
不得只写“继续完善项目”，也不要求接手者重新阅读全部历史聊天。


## 后端先行与跨会话管理

实施计划区分 backend、frontend、integration 的交付目标，先后端验收再前端实现；阶段内任务颗粒度、安排与验证策略由模型决定。
每版 draft/execution-plan.json 参考 execution-plan.example.json，明确 source_roots 与默认后端后暂停。
每个有效 AC/gate 必须有 phase；每个任务必须有 phase、baseline_ref、depends_on 与证据。

### 可合并到 04-architecture / 06-implementation / 09-release-plan 的语义单元

后端边界：模块、API/事件、持久化/事务/迁移、鉴权、错误/幂等、运行与独立验收方式。
前端边界：路由/组件/状态、生产 API 客户端、鉴权/代理/CORS、交互状态、真实后端对接与 UI 验收。
交接协议：后端 hNNN 内容、版本/契约/源码标识、环境与启动/种子/冒烟、known limitations；必需能力缺失阻止交接。
三阶段验收：后端独立测试、前端真实 API 与交互、完整系统回归/升级，不能互相冒充。
调整策略：实现缺陷修复 vs 规范修订，旧 hNNN 失效和新前端绑定如何处理。
跨会话：state/tasks/decisions 是工作状态主源，session-notes 和 checkpoint 引用本版规范，不重抄整套规范。

交接材料使用 backend-handoff.template.md；检查点摘要使用 session-notes.template.md。
正式后端与前端实现文件在应用源码目录，不写进冻结文档快照充当代码仓库；快照内 prototype 仍是设计基准。
