# INTEGRATION_VERIFY / DELIVERED：完整系统验证与归档

验证方法遵循 [implement.md](implement.md)。本文件保留完成标准、证据与归档要求，不强制固定测试组合或审查流程。

后端交接成功只代表后端门槛，前端验收成功只代表前端门槛；两者都不直接等于系统交付。
当前版本在 INTEGRATION_VERIFY 才可 deliver；可以在这阶段的任意中途保存检查点和新会话续接。

## 组合身份与真实证据

最终报告绑定产品版本、bNNN 与 manifest_sha256、准确的系统 code_ref、后端 hNNN 及其 manifest hash、两端实际源码指纹。
系统 code_ref 应可定位两端组合，例如发布清单引用两个实际提交/构建摘要及未提交快照，而不是仅写前端 HEAD 或一个会移动的分支名。
工具 source_fingerprints 直接观察 execution-plan 指定路径，忽略规定的依赖/输出/本地秘密；它不能验证远程部署或未纳入观察范围的代码。
若测试后代码改变，取得新证据并更新报告，不能给旧日志重贴新的 code_ref 冒充重新执行。
本地环境秘密、实际服务/数据库状态不从代码 hash 推断，新会话需重新核对。

## 必需系统验证

按基线执行完整有效需求验收、本期新行为、旧功能回归、关键失败路径、角色/租户隔离、真实前后端链路。
根据批准矩阵检查干净安装、指定父版带数据升级、仍支持的旧客户端/事件消费者、混合部署窗口、迁移中断后重试和允许的应用回退/前滚恢复。
数据库可逆性与应用可回滚是不同问题；不可逆迁移的备份/恢复、损失风险与批准前提必须早已明确，不编造无损回滚承诺。
无适用某项变化时在基线写明理由，不在交付当下偷偷降级门槛。
最终报告需要包含所有有效 required AC/gate 的适用证据，覆盖 backend/frontend/integration，而不只有页面截图或一份“全部通过”的概述。
单项证据可支撑多个检查，但必须真正含相应结果；不得用“之前已通过”继承状态。重用证据需证明相同代码/环境/检查范围有效，不改日志冒充执行。

## 自主完成检查

综合判断实现是否符合完整规范、本期差异和批准原型，以及改动的工程质量与重要风险；不能只凭构建成功认定交付。
检查方式、时机、工具和是否拆成独立审查由你选择，可合并重复验证。保留已批准的必需检查及其对应结果，不虚构独立审查或多 Agent 验证；修复问题后取得适用证据。
后端代码需要改时回 reopen-backend，hNNN 更新，前端对接与组合证据重新建立；公共语义改变先 revise。

## 归档

final verification.json 使用 schema_version=4、phase=integration；各 check 的 code_ref 绑定同一组合身份，证据文件位于本版 evidence/。
前端阶段报告与其证据从进入 INTEGRATION_VERIFY 后不能被悄悄改动；需重验时回 FRONTEND_BUILD/VERIFY。
所有本版任务完成且绑定当前基线，必需验收实际通过后，展示成果、报告和限制，询问“归档本次交付并进入 DELIVERED，还是继续修改？”用户确认后才 deliver 复制报告、任务与证据到 delivery/，保留后端 implementation/backend/hNNN 包并校验引用。
check-delivery 检查归档完整性，不要求正在研发的工作区仍保持旧源码；历史校验不误用当前源码。

DELIVERED 不等于生产部署。发布、流量切换、生产迁移、付费资源与秘密获取仍需独立授权。
current_delivered 文档指针通过明确 promote 更新，不因维护补丁自动回退主线。源码合并/checkout/部署均不是该命令的效果。
已交付版本后续行为/规范纠错创建下一产品或补丁版本，保留历史，不回写原版。

## 交付说明

说明版本与基线、两端准确代码标识、完成范围、保留行为、启动/升级方式、真实验收证据与限制，给出版本索引和继续下一版入口。
未执行、环境缺失、skipped 或仅 mock 成功不是通过；工具检查的是断言和字节，Agent 对执行事实负责。
