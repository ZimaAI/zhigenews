# FRONTEND_READY → FRONTEND_BUILD → FRONTEND_VERIFY

实施方法遵循 [implement.md](implement.md)。本文件约束真实对接和阶段边界，不固定开发与验证步骤。

## 可以在全新会话开始

先按 sessions 恢复版本，读取当前批准快照中的需求、UX、领域/契约、本期差异和实施计划；再读活动后端 hNNN 的 HANDOFF、handoff.json、逐接口清单、运行/鉴权/冒烟说明与验收结果。
不用阅读所有后端源码才能对接；从这些明确边界开始，仅在定位缺陷时读相关后端实现。
执行 check-backend 的 live 检查；核对 backend source_roots 对应真实代码、共享配置、依赖锁和迁移脚本。工具只比较声明的受管路径，遗漏路径无法被它自动发现。
新会话重新检查实际服务状态和协议：启动/连接的是哪一后端修订、base URL、端口/代理、CORS、cookie/CSRF/token、数据库与测试角色。健康检查只证明存活，不代表全部业务正确。
旧会话的 localhost、PID、浏览器状态、临时 token 不可假定仍有效。缺环境时记录阻塞；可以做不依赖该环境的已授权工作，但真实集成未执行不能通过门槛。

## 开始前端的权限与项目结构

后端接受后取得 frontend 授权，绑定同一 bNNN 和当前 hNNN 的指纹。仅“后端完成”不等于前端已获授权。
可沿用真实来源记录中的明确条件实施授权，但阶段末尾默认仍展示结果并询问；只有当前转换已明确确认或用户明确免除具体范围的重复询问，才不再重复提问。若只是“先实现后端，完成后停下”，必须停下。
新会话继续已经在 FRONTEND_BUILD 的工作，不应要求重新批准全部需求。当前用户要求暂停优先。
前后端可以是一个仓库，也可以是工作区下的两个独立仓库：

```text
workspace/                       # --root 指向这个共同父目录
├── .project-flow/
├── docs/releases/
├── backend/                     # 可以包含自己的 .git
└── frontend/                    # 可以是新创建的前端仓库
```

换机器时复制/取得这一文档状态与精确源码，或恢复为等价的相对布局；不要自动 clone/checkout/reset。
当前本地工具按工作区相对 source_roots 校验，不自动适配任意外部路径或仅可访问 URL、无法取得源码的服务；这类环境先记录限制并完成明确的交接核对，不伪造 live source 检查。

## 自主实现与对接

依据已批准原型、契约和真实后端，自主决定页面/组件组织、状态管理、客户端实现及验证方法，连续完成本期前端范围；不要求固定切片或组件到页面的开发顺序。
phase=frontend 的任务可依赖已完成后端任务；任务细化由你决定，不能以永久 mock 代替真实对接。
单元测试可以使用受契约校验的替身；演示模式与正式运行模式明确隔离。正式默认传输是实际 API；连接失败必须显示真实失败，禁止悄悄 fallback 到假成功。
不通过前端隐藏控件代替后端授权，不硬编码演示身份或密钥，不读数据库直连代替已经批准的后端接口。
保留已批准的视觉/交互：加载、空、错误、权限拒绝、分页、重试、乐观更新/一致性、移动适配、可访问性等按需求实现。

## 接口缺口与代码修复

后端实现不符合原契约：登记具体复现与影响，reopen-backend，在后端阶段修复、验收并产出新 hNNN；前端已完成代码保留，任务重新判定，不能悄改服务后继续使用旧交接。
前端想改变接口/字段语义/业务规则：先 revise，更新原型、领域、契约和验收，新 bNNN 重新批准；不能用“方便前端”覆盖设计。
前端实现错误：在 FRONTEND_BUILD/VERIFY 内修复，不改变原规范、不使后端包失效。影响共享配置时检查后端 source_roots 指纹和真实影响。
新 hNNN 不继承对旧 hNNN 的前端授权/验收记录；准确展示差异后重新绑定。当前用户的前端对接指令可作为真实授权来源，不编造新用户消息。

## 前端验收与系统验收是两件事

自主选择适合技术栈与风险的验证方式，证明前端可运行、符合批准交互且能正确对接真实 API。组件、类型、静态、构建、浏览器或视觉检查按项目要求与实际需要选择；已批准的必需检查不能自行省略。
报告绑定当前 bNNN、hNNN、前端代码标识与源码指纹，使用 phase=frontend 的必需 AC/gate。
全部前端任务完成并提供真实报告后，询问进入 INTEGRATION_VERIFY 还是继续调整前端；选择推进后才运行 stage，进入不是完成。
最终系统验收按 delivery 检查完整业务、回归、两端组合和适用升级路径；不得把前端单测通过当整系统通过。
每个有意义回合更新任务/证据并 checkpoint，可在前端实现或验收的任意中途新开会话继续。

## 前端收尾确认

FRONTEND_READY 中展示准确后端 hNNN、原型与前端范围，询问开始前端还是先调整/暂停。
FRONTEND_BUILD 已具备验收条件时，展示页面入口和实际已运行检查，询问进入 FRONTEND_VERIFY 还是继续修改。模型不必在每个组件和测试后提问，只在正式阶段边界询问。
出现后端缺陷或规范变化仍走受控回退，不把用户选择“继续修改前端”扩张为修改公共契约的批准。
