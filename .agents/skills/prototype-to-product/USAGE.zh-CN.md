# 使用手册：启动、换会话、进入下一阶段

这里的 v1.0.0/b001、v1.1.0 只是示例，使用时以当前工作区的实际版本和候选为准。
通常不需要你编辑 JSON、执行脚本或记住状态命令。你发自然语言，AI 检查门槛、更新状态和交接记录。
这些提示不是任何真实项目的授权；AI 不能把本文示例复制到批准记录充当用户原话。

## 0. AI 会主动问，不再让你猜阶段是否结束

当它判断当前阶段已具备收尾条件，会先核查实际成果与证据，然后主动询问：

```text
当前：v1.0.0 / b001 / SPECIFY
本阶段成果：<实际文档、契约和验收范围及入口>。
核查结果：<真实检查；未执行项和限制不隐瞒>。

是否批准这份 v1.0.0/b001 规范并进入 READY，
还是继续修改当前文档？也可以先停在这里。
进入 READY 只确认文档，不会启动正式实现。
```

你可以直接回复“进入下一阶段”“先修改激活码的有效期规则”“先停在这里，下次继续”。明确的待确认问题会说明该回答的实际作用；你不需要操作管理脚本。
选择进入后，AI 核对条件并执行对应转换；选择修改则保持阶段或按规范规则受控回退，修改完成再问；选择暂停则保存并停止。
没有回复之前不推进，不后台执行下一阶段。尚有可完成任务时继续工作，不每个文件/测试都请求阶段确认；验证失败时先修复或说明真实阻塞，不假称可进入下一阶段。
确认点 qNNNN 保存在 state.pending_stage_review，与规范 bNNN、产品版本分开。换会话恢复同一问题；已回复且内容没变时不重复审批，内容改变则展示变化后重新确认。

## 1. 首次创建项目

在能够访问项目文件的工作区中打开 Codex，会话内输入：

```text
$prototype-to-product

我要从 0 到 1 开发【项目描述】，首个产品版本为 v1.0.0。
先与我讨论并迭代可运行前端原型、领域模型与数据契约。
每轮同步修改受影响的页面、规则、数据与验收例子。
我明确要求定稿前，不进入正式实现。
```

AI 初始化当前格式的受管目录，从 DISCOVER 明确足够信息后，主动询问开始 ITERATE 原型还是继续调整范围，得到选择再进入。不需要第一轮回答完所有细节。
普通项目源码和依赖可以按实际技术栈组织；本包不导入其他格式的 workflow 状态。

## 2. 随时结束本次工作并准备换会话

```text
保存当前版本检查点，记录已完成内容、未完成任务、失败验证、
当前代码状态和下一条具体动作，并给出新会话续接提示。
保持当前阶段，不因为我要换会话而推进阶段。
```

AI 应更新 state/tasks/decisions/handoff、会话笔记和 checkpoint。你无需一直保留聊天。
即使不发这句话，AI 也应在有意义的工作结束或阶段切换时保存；突然中断时只能从已经落盘的内容恢复，不能恢复不存在的聊天信息。

## 3. 新会话继续之前未完成的阶段

在 **同一项目工作区** 打开新会话：

```text
$prototype-to-product

继续当前项目未完成的任务。
先读取 .project-flow/RESUME.md 和注册表，恢复当前活动版本；
运行 resume，核对阶段、基线、任务、检查点与实际文件。
沿用仍然有效的决定和授权，不新建版本，不重新从零规划。
按记录继续当前阶段；若有待确认的阶段收尾选择，先恢复这个选择点，
说明当前成果和下一步，询问我进入下一阶段还是继续修改。
```

同时有多个产品版本时加一句：“本次继续 v1.1.0。”明确版本优先，不按目录大小或更新时间猜。
resume 是只读检查，不恢复旧源码。检查点后文件变化就核对当前差异，不拿旧摘要覆盖现有修改。
没有检查点：读取 state/tasks/decisions/handoff 与实际代码，补最小上下文后继续，不要求重讲整个项目。
跨设备必须带齐 docs、.project-flow、源码、依赖说明及未提交修改；仅导出基线文档不足以续接全部执行进度。

### 只查看进度，不继续执行

```text
$prototype-to-product

只查看当前项目状态，不修改任何文件或推进阶段。
告诉我当前版本、阶段、已完成和未完成事项，
以及进入下一阶段还需要哪些产物或我的批准。
```

### 新会话继续 SPECIFY 的未完成文档

```text
$prototype-to-product

继续 v1.0.0 的 SPECIFY 阶段。
读取现有原型、数据契约、决定记录和文档缺口，继续完善完整规范。
只补缺口和受影响内容，不重新采访已确认事项。
准备好后展示实际候选基线与文档入口；先不要批准，也不要实现。
```

### 新会话继续写到一半的后端

```text
$prototype-to-product

恢复 v1.0.0 当前后端阶段，从未完成任务或失败验证继续。
沿用可核对的有效后端授权，不重做已完成内容，不实现正式前端。
具体实现、测试与验证方法由你根据项目自主决定。
后端验收和交接完成后，停在 FRONTEND_READY。
```

## 4. 怎么进入下一个阶段

**阶段转换依赖产物和授权，不是直接修改一个字符串。** “继续”只延续已有范围；需要产品批准或另一端授权时，AI 不能自行代替你决定。

| 当前 | 你可以说 | AI 到哪里停 |
| --- | --- | --- |
| DISCOVER/SCOPE | 信息足够了，先做第一版/本期原型给我看。 | ITERATE，进入讨论 |
| ITERATE | 原型和数据设计可以定稿，进入 SPECIFY 整理文档，先不要实现。 | SPECIFY，候选待审阅 |
| SPECIFY | 批准已展示的 v1.0.0/b001 文档基线，进入 READY，先不实现。 | READY，后端未开工 |
| READY | 按已批准基线开始后端实现，阶段末尾询问我。 | BACKEND_BUILD，收尾时询问是否进入验收 |
| BACKEND_BUILD | 继续完成后端，到收尾时展示成果和进入验收的选择。 | 先保持 BACKEND_BUILD，确认后进入 BACKEND_VERIFY |
| BACKEND_VERIFY | 修复后端验收问题，通过后展示交接候选。 | 确认接受交接后 FRONTEND_READY，不代表整系统完成 |
| FRONTEND_READY | 核对已验收后端，开始正式前端实现与对接。 | FRONTEND_BUILD，后续阶段末尾仍询问 |
| FRONTEND_BUILD/FRONTEND_VERIFY | 继续前端未完成任务和失败验证。 | 收尾时询问进入前端验收/系统验收，或继续修改 |
| INTEGRATION_VERIFY | 完成剩余系统验收，展示结果并询问我是否归档。 | 条件满足且用户确认后 DELIVERED，不部署生产 |
| BLOCKED | 已提供【解决条件】，请核对并恢复原阶段。 | 验证阻塞解除后返回 resume_stage |
| DELIVERED | 基于本次交付规划下一产品版本。 | 新产品版本 SCOPE，不覆盖历史 |

同范围的实现→验证不需要重新申请全部开发权限，但阶段末尾仍默认询问是否推进或修改；阶段内不逐任务批准。后端验收→前端开工另需前端授权，可另起会话发出。
用户明确限制“只做某项验证”或“暂不归档”时，AI 遵守限制，不自动扩大范围。

## 5. 专门说明：SPECIFY 怎样进入 READY

### 两个状态的区别

SPECIFY 表示正在整理/审阅规范，可能尚未完成，也可能已有候选等待批准。
READY 表示 **你已经批准具体文档基线，但尚未授权正式后端实现**。
生成文件、完成 seal、保存检查点或打开新会话，都不等于批准。

### 情况 A：文档没有整理完，或还没有候选号

```text
继续完善当前版本的 SPECIFY 文档并检查一致性。
补齐阻塞问题，完成后冻结并展示实际候选基线、范围摘要和文档入口。
暂时保持 SPECIFY，等我审阅批准，不实现。
```

AI 真实核查后运行 seal，得到例如 v1.0.0/b001，展示给你，并主动问“批准这份基线进入 READY，还是继续修改规范？”此时仍是 SPECIFY，保存待确认选择后结束本轮。
存在需要你决定的高影响问题时，AI 给出具体问题和建议；不能假装缺口已经解决。

### 情况 B：候选已经展示，你认可且不要求修改

```text
我批准已展示的 v1.0.0/b001 文档基线。
请记录这次批准，将当前版本推进到 READY，保存检查点。
暂时不要实现后端或前端。
```

AI 检查候选引用、草稿与快照一致、无阻塞，记录对当前确认点的回答，再调用 approve --kind baseline，成功后进入 READY。
不必为了批准再创建 b002。你可以在此结束会话，下一会话恢复 READY 后再决定开工。

### 情况 C：你想批准后直接开始后端

```text
我批准已展示的 v1.0.0/b001 文档基线，并授权按它开始后端实现。
由你自主决定实现、测试和验证方法。
后端验收、生成交接并保存检查点后，停在 FRONTEND_READY。
暂不实现正式前端，不执行生产部署。
```

AI 顺序记录 baseline 和 backend 两项授权，先到 READY 再到 BACKEND_BUILD，不需要额外让你重复确认这两个刚指定的转换。之后后端实现、验收等新的收尾点仍默认询问，除非你明确免除这些具体阶段范围的重复提问。
前提是该基线真实存在、已经展示且未变化；不能把对“以后整理出的任意文档”的笼统许可当作精确批准。

### 情况 D：想进入 READY，但还要改需求

```text
先在当前版本调整【内容】，同步规范、原型、契约与验收。
保留历史基线，形成新候选并展示差异给我。
不要沿用旧批准，也不要进入正式实现。
```

确认新候选后才进入 READY。不要先批准旧版再悄悄加入变化。

## 6. READY 后怎么在新会话开始后端

```text
$prototype-to-product

恢复当前版本，核对已经批准的具体文档基线。
授权按该基线开始后端实现，不做正式前端。
由你自主决定实现、测试与验证方案，完成全部批准的后端范围。
验收后生成接口、运行、鉴权、测试数据和冒烟说明等交接资料，
保存检查点，停在 FRONTEND_READY。
```

已处 BACKEND_BUILD 时“继续后端”沿用有效授权；已处 READY 时上面的“授权开始后端”才代表新阶段开工。

## 7. 后端完成，新会话开始前端

```text
$prototype-to-product

恢复当前版本，核对 FRONTEND_READY 状态和已验收的后端交接包。
授权开始正式前端实现，并完成后续本地系统验证与交付归档。
先读取批准原型、完整规范、权威契约和实际后端交接，
运行 check-backend，并实际检查服务、地址、环境和鉴权。
按照已批准设计对接真实 API；具体实现、测试和验证方法由你决定。
不使用 mock 冒充集成，不擅自修改后端公共接口。
不执行生产部署；有不能自行解决的阻塞就准确记录。
```

check-backend 检查文件记录和源码指纹，不证明实际服务还在运行。新会话仍需重新检查运行环境。
原规范没变但后端实现有缺陷：回后端修复/重验，生成新 hNNN；公共语义需变化：先 revise 新规范基线。

## 8. 多版本迭代与换阶段的区别

```text
基于已交付 v1.0.0 的精确基线规划 v1.1.0。
本期新增【功能】，保持其他行为；先讨论受影响原型和数据设计。
继承完整规范，不继承任务完成、授权、后端交接或测试通过状态。
```

v1.1.0 是产品版本；b002 是规范基线；h002 是后端交接；c0004 是会话检查点。
换会话不新建产品版本；未交付产品的规范修订增加 bNNN；交付后继续变化才新建产品/补丁版本。
本包无其他格式的 Skill 状态接入，不影响这些由当前格式创建的产品迭代。

## 9. 常见卡点

| 情况 | 正确处理 |
| --- | --- |
| 新会话找不到 RESUME | 找注册表及目标版 state/tasks/decisions/源码恢复；真实资料缺失时说明缺哪些 |
| 候选号不知道 | 让 AI 只读状态，展示当前 candidate 和文档入口，不从目录名猜 |
| SPECIFY 一直没到 READY | 看是文档缺口、未决问题、未 seal，还是只缺你批准具体候选 |
| READY 说“继续”没开工 | 明确说“授权按已批准基线开始后端”；准备就绪不等于开工许可 |
| 更改了已冻结文档 | revise/新候选/重批准，不覆盖旧快照或转移批准 |
| 测试没通过 | 自主修复或准确记录环境阻塞，不删掉必需验收 |
| 不受支持的管理格式 | 停止并保留原资料；本包不提供转换，不手工重标格式号 |
| 想在两个会话同时改同一工作区 | 不按并行安全系统使用；默认顺序交接和单写者 |

完整参数见 [工具手册](references/tooling.md)。审批与阶段脚本负责记录和校验，不代替你的真实决定或项目测试。

## 10. 暂时减少阶段收尾提问

默认每个正式阶段收尾都询问。日常“完整实现”“自主测试”不关闭这一默认行为。
已经批准精确方案后，你可以明确指定范围，例如：

```text
本次后端 BUILD → VERIFY → FRONTEND_READY 连续推进，不再逐阶段询问。
实现、测试和修复方法由你决定；全部后端验收通过后归档交接并停下。
不允许跳过必需验收，也不修改批准方案，不开始正式前端。
出现阻塞或需要改变方案时向我说明。
```

AI 记录这条真实指令与停止点，只在指定范围内免除重复提问。新基线、交接或需求范围发生变化时重新确认。恢复默认只需说“之后每个阶段末尾都先问我进入还是修改”。
